# 만능 프롬프트 템플릿

> 6요소 **역할 · 맥락 · 지시 · 형식 · 제약 · 예시**에 **검증**을 더한 템플릿입니다.
> 칸을 다 채울 필요는 없습니다. 필요 없는 칸은 지우세요. 짧은 질문이라면 3줄 버전으로 충분합니다.
> 각 요소가 왜 필요한지는 [docs/02-prompt-anatomy.md](../docs/02-prompt-anatomy.md)에 정리했습니다.

---

## 1. 3줄 버전 (일상용)

```text
[목표] ___을(를) 위해 ___을(를) 해줘.
[맥락] 읽을 사람은 ___이고, 지금 나는 ___ 상황이야. 참고 자료: ___
[형식] ___ 형식으로 ___ 분량이면 돼. 확실하지 않은 내용은 "확인 필요"라고 표시해줘.
```

**예시**

```text
[목표] 팀장님께 프로젝트 일정이 1주 늦어진다고 알리는 메일을 써줘.
[맥락] 팀장님은 결론부터 듣는 걸 좋아하셔. 지연 이유는 외부 API 승인 대기야. 대안으로 범위 축소안이 있어.
[형식] 5문장 이내, 정중하지만 군더더기 없이. 제목도 하나 붙여줘.
```

## 2. 전체 버전 (중요한 작업용)

자료가 길면 **자료를 위에, 질문을 아래에** 두세요. Anthropic은 이렇게 하면 답변 품질이 최대 30%까지 좋아진다고 밝혔습니다.

```xml
<role>
(선택) 너는 ___ 분야의 ___야.
※ 말투와 관점을 정할 때 쓰세요. 정답률을 올려주지는 않습니다. (docs/10 참고)
</role>

<context>
- 목적(왜 하는지):
- 독자/사용처:
- 현재 상황·배경:
- 이미 정해진 것 / 이미 해본 것:
</context>

<documents>
<document index="1" source="파일명 또는 URL">
(여기에 자료 붙여넣기)
</document>
</documents>

<task>
1.
2.
3.
완료 기준(Done when): ___이면 끝난 것으로 본다.
</task>

<format>
- 구조: (예: 표 1개 + 요약 3줄 / 섹션 제목 + 불릿)
- 분량:
- 어조:
</format>

<constraints>
- 반드시 지킬 것:
- "하지 마" 대신 "이렇게 해"로 쓰기: (예: "전문용어 금지" → "중학생이 이해할 단어로")
- 근거 규칙: <documents>에 없는 내용은 추측하지 말고 "자료에 없음"이라고 표시해.
</constraints>

<examples>
<example>
입력: ...
출력: ...
</example>
<example>
입력: ...
출력: ...
</example>
</examples>

<before_answering>
요청에 모호한 부분이 있으면 답하기 전에 가장 중요한 질문을 최대 3개 먼저 해줘.
모호하지 않으면 바로 진행해.
</before_answering>

<self_check>
답을 내기 전에 <task>와 <constraints>를 한 항목씩 대조해서 빠진 것이 없는지 확인해줘.
확인하지 못한 항목이 있으면 답 끝에 따로 적어줘.
</self_check>
```

## 3. 칸별 작성 요령

| 칸 | 꼭 써야 할 때 | 흔한 실수 |
|---|---|---|
| `role` | 말투나 관점, 전문 분야의 어휘가 중요할 때 | "세계 최고의 전문가"라고 쓰면 정확해진다고 믿기 |
| `context` | **거의 항상** | 내 머릿속에만 있는 배경을 AI도 안다고 가정하기 |
| `documents` | 사실 정확도가 중요할 때 | 자료 없이 "최신 정보"를 물어보기 |
| `task` | 항상 | 한 번에 여러 일을 섞고, 완료 기준은 쓰지 않기 |
| `format` | 결과를 다른 곳에 붙여 넣을 때 | 형식을 정하지 않고 나중에 다시 고쳐 달라고 하기 |
| `constraints` | 꼭 지켜야 할 규칙이 있을 때 | 대문자나 "절대!!!" 같은 강조를 남발하기 (최신 모델은 과하게 따름) |
| `examples` | 원하는 스타일이나 형식을 말로 설명하기 어려울 때 | 예시를 1개만 주기 (그대로 베낍니다) |
| `before_answering` | 요청이 크거나 모호할 때 | 간단한 일에도 질문부터 하게 만들기 |
| `self_check` | 요구사항이 5개 이상일 때 | "정말 확실해?"로 검증을 대신하기 (오히려 정답을 뒤집음) |

## 4. 추론(Thinking) 모델을 쓸 때 덜어낼 것

- "단계별로 생각해(think step by step)"는 지우세요. 추론 모델은 알아서 생각하며, 이 문구를 넣어도 효과가 거의 없습니다.
- 절차를 하나하나 지시하는 대신 **목표와 완료 기준**을 명확히 쓰세요.
- 예시는 먼저 없이 시도해 보고, 결과가 원하는 형식과 다를 때만 추가하세요.
- 깊게 생각하게 하고 싶으면 문구보다 앱이나 API의 **추론 강도(effort/thinking) 설정**을 쓰세요.
